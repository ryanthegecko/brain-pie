# Brain Pie API — Primer for Automated Access

This document is for a Claude Code instance (or any agent) that needs to read and write Brain Pie data on behalf of the user.

---

## Base URL

```
https://brain-pie-license.brainpie.workers.dev
```

---

## Authentication

Every request must include an API key as a Bearer token:

```
Authorization: Bearer <api-key>
```

The user's API key and user ID are stored in their browser's localStorage under:

- `brainPie_apiKey` — the Bearer token
- `brainPie_apiUserId` — the stable user ID (doesn't change on key rotation)

The user can also find both values in the app at **Settings → API Access**.

---

## Endpoints

### `GET /api/pies/:id`

Fetch a pie's full JSON by its ID.

```sh
curl https://brain-pie-license.brainpie.workers.dev/api/pies/<pieId> \
  -H "Authorization: Bearer <api-key>"
```

- `200` — pie JSON body
- `401` — missing or invalid key
- `404` — pie not found (wrong ID, or belongs to a different user)

---

### `PUT /api/pies/:id`

Replace a pie's full JSON content.

```sh
curl -X PUT https://brain-pie-license.brainpie.workers.dev/api/pies/<pieId> \
  -H "Authorization: Bearer <api-key>" \
  -H "Content-Type: application/json" \
  -d '<pie JSON>'
```

- `200` — echoes the stored JSON back
- `400` — body isn't valid JSON, or is missing a `categories` array
- `401` — missing or invalid key

The body must be the **complete** pie JSON (not a patch). Always GET first, modify in memory, then PUT the full object back.

---

## Finding Pie IDs

Pie IDs are UUIDs generated by the app. The user can find them in their browser:

```js
// Open the browser console on brainpie.app and run:
JSON.parse(localStorage.getItem('brainPie_meta'))
// → { pieIds: ["abc-123", ...], pieNames: { "abc-123": "Life Pie" }, activePieId: "abc-123" }
```

The `activePieId` is almost always the one to use. The user should paste it to you directly — asking them to open the console and run the above is a reliable way to get it.

## Data Format

The pie JSON body looks like this:

```json
{
  "categories": [
    {
      "id": "cat-uuid",
      "name": "Work",
      "color": "#4CAF50",
      "items": [
        {
          "id": "item-uuid",
          "name": "Projects",
          "percentage": 40,
          "color": "#66BB6A",
          "subItems": [
            "Simple spoke (legacy string format)",
            {
              "text": "Launch v2",
              "type": "single",
              "scheduled": {
                "date": "2026-07-01",
                "time": "09:00",
                "duration": 60,
                "allDay": false,
                "calendarEventId": null
              },
              "metadata": { "calendarEventId": null, "recurrence": null }
            },
            {
              "text": "Marketing plan",
              "type": "list",
              "children": [
                { "text": "Write copy", "children": [] },
                { "text": "Design assets", "children": [] }
              ],
              "metadata": { "calendarEventId": null, "recurrence": null }
            }
          ]
        }
      ]
    }
  ],
  "categoryPercentageOverrides": {
    "cat-uuid": 45.5
  },
  "priorityList": []
}
```

### Hierarchy

| Level | Key in JSON | Notes |
|---|---|---|
| Category | `categories[]` | Top-level area of life. Has `id`, `name`, `color`, `items`. |
| Slice | `items[]` | Domain within a category. Has `id`, `name`, `percentage`, `color`, `subItems`. |
| Spoke | `subItems[]` | Can be a plain string (static, no schedule) or an object (see below). |
| Action | `children[]` | Sub-tasks under a List spoke. |

### Spoke types

| `type` | Has `children`? | Schedulable? |
|---|---|---|
| `"static"` | No | No |
| `"single"` | No | Yes — `scheduled` on the spoke itself |
| `"repeating"` | No | Yes — `metadata.recurrence` + optional `scheduled` |
| `"list"` | Yes (`children[]`) | Children have their own `scheduled` |

A plain string in `subItems` is treated as `static`.

### IDs

- Use `crypto.randomUUID()` (or any UUID v4 generator) for new `id` fields on categories and slices.
- Spoke objects don't need an `id` field — they're referenced by index.

### Percentages

- Slice `percentage` values within a category should sum to 100.
- If you add or remove slices, redistribute the percentages to keep the sum at 100.
- `categoryPercentageOverrides` is optional. Omit it or leave it as `{}` if you don't need manual category sizing.

## Recommended Workflow

1. **GET** the current pie to read its state.
2. Parse the JSON and make your modifications in memory.
3. **PUT** the full modified object back.
4. Tell the user what changed — the app will reflect the new data on next page load (or immediately if they're using Firebase sync and reload).

### Example: add a spoke to an existing slice

```python
import httpx, json, copy

API = "https://brain-pie-license.brainpie.workers.dev"
KEY = "<api-key>"
PIE_ID = "<pie-id>"

headers = {"Authorization": f"Bearer {KEY}", "Content-Type": "application/json"}

# 1. Fetch
pie = httpx.get(f"{API}/api/pies/{PIE_ID}", headers=headers).raise_for_status().json()

# 2. Modify — find the slice by name and append a spoke
for cat in pie["categories"]:
    for item in cat["items"]:
        if item["name"] == "Projects":
            item["subItems"].append({
                "text": "New spoke from API",
                "type": "static",
                "metadata": {"calendarEventId": None, "recurrence": None}
            })

# 3. PUT back
result = httpx.put(f"{API}/api/pies/{PIE_ID}", headers=headers, json=pie).raise_for_status().json()
print("Done — spokes now:", [s if isinstance(s, str) else s["text"]
                              for cat in result["categories"]
                              for item in cat["items"]
                              for s in item["subItems"]])
```

---

## Notes

- **Always PUT the full pie object** — there is no partial-update (PATCH) endpoint.
- **Preserve unknown fields** — do a GET, modify only what you need, and PUT the whole thing back. Don't reconstruct the object from scratch or you'll drop fields the app added.
- **`null` not `undefined`** — when constructing new objects use `null` for absent optional fields (e.g. `"calendarEventId": null`). The storage layer is Firebase-compatible and rejects `undefined`.
- **The API store is separate from Firebase sync** — if the user has Firebase cloud sync enabled, changes via the API won't appear in Firebase and vice versa. The intended use is localStorage-mode users, or as a machine-readable snapshot layer.
